# Feature: fanout-engine (F04–F07, F09)

> Status: Approved (2026-10-31; изменено после ревью R1/R2/R3/R5: FR-002, FR-006, FR-008, FR-009, FR-010, FR-011, Q-002 — одобрено владельцем; R5: FR-011-триггер по единому критерию Q-002, FR-010 дополнен терминальным usage упавших попыток и нулями адаптера)
> Source: @[../../PLAN.md] · @[../../ideas/001-fusion-mode-for-pi.md]
> Last Updated: 2026-10-31

## Overview

Движок fan-out расширения pi-fusion: тул `fusion_delegate`, который главная сессия
(лид) вызывает для делегирования независимых частей работы; исполнительный слой —
клиент delegation-шва pi-subagents, пул ширины и структурные отчёты воркеров.
Покрывает фичи F04 (контракт тула), F05 (шов-клиент), F06 (пул ширины),
F07 (схема отчёта воркера), F09 (деградация). Для оператора это выглядит как один
вызов тула, который возвращает таблицу результатов по каждой задаче.

## Business Context

- **Problem:** фронтир-модель в главной сессии исполняет всю рутину сама — дорого и
  медленно; мультиагентного fan-out «из коробки» в pi нет.
- **Users:** оператор (владелец) через лида; воркер-модели как исполнители.
- **Value:** рутина уходит на дешёвую ногу, лид сохраняет план/ревью; экономика
  «price per task» вместо «price per token».
- **Success signal:** живой прогон: лид делит задачу на ≥ 2 части, воркеры исполняют
  параллельно, отчёты возвращаются, лид отвечает; смоук-тесты на fake-pi зелёные.

## Goals

- Одна вызов-семантика atomic-agent: контракту `fusion.delegate` дословно, частичные
  результаты не валят вызов, порядок результатов = порядок задач.
- Управляемая ширина: лид выбирает, система честно клампит (физика машины) и
  объясняет причину клампа в результате.

## Non-Goals / Out of Scope

- Approval/standing-yes и скоуп-чек — спека 003 (F10, F11).
- Гайданс `### fusion`, конфиг-команда, агент-файл — спека 002 (F01–F03, F08, F19).
- Маршрутизация `contract.provides[].shape` в брифы зависимых — F16 (Phase 3).
- Верификация в копии (F20), живые строки воркеров (F15).
- Рекурсивное делегирование воркерами — исключено конструктивно (allowlist агента).

## User Stories

### US-001: Лид раздаёт независимые части работы

**As a** лид (фронтир-модель в главной сессии)
**I want to** вызвать один тул со списком задач
**So that** независимые части исполнятся параллельно дешёвыми воркерами, а я получу
все результаты одним результатом тула.

**Acceptance Criteria:**
- [ ] Каждая задача исполняется отдельным fresh-воркером; воркеры работают
      concurrently в пределах ширины
- [ ] Результат тула содержит по каждой задаче статус, summary, filesChanged
- [ ] Отказ части задач не делает весь вызов ошибкой

### US-002: Лид видит честную ширину

**As a** лид
**I want to** задать `maxWorkers` и узнать, если система ограничила ширину
**So that** я могу перепланировать (дробить задачи, повторить позже).

**Acceptance Criteria:**
- [ ] Фактическая ширина ≤ min(maxWorkers, число задач, maxParallel, per-model cap)
- [ ] Если кламп сработал — в результате названа причина и значение

### US-003: Кривой отчёт воркера не теряет работу

**As a** лид
**I want to** отличить «воркер сделал, но криво отчитался» от «воркер не сделал»
**So that** я не пере-имплементирую сделанное.

**Acceptance Criteria:**
- [ ] Невалидный отчёт → ровно один перезапрос отчёта у того же воркера
- [ ] Повторный провал → статус failed с пометкой schema-missing (работа на диске
      сохраняется, лид предупреждён)

### US-004: Деградация вместо молчаливой поломки

**As a** лид
**I want to** получить действенный отказ, если делегирование недоступно
**So that** я сделаю работу сам, а не зависну в ожидании.

**Acceptance Criteria:**
- [ ] Шов отсутствует → тул отвечает «fusion недоступен — делай работу сам»
- [ ] Шов отвечает unavailable_context → то же, с пометкой seamUnavailable

## Functional Requirements

### FR-001: Контракт делегирования — Must Have

WHEN лид вызывает `fusion_delegate` с валидным контрактом
`{ tasks: [{ id, instructions, title?, deliverable?, files?, maxSteps?, timeoutMs? }], maxWorkers?, contract? }`
THE SYSTEM SHALL исполнить каждую задачу как отдельный ephemeral fresh-воркер
(агент `fusion-worker`, модель из ротации, cwd сессии) и вернуть по-задачные
результаты
SO THAT независимые части исполняются параллельно без потери контекста лида.

### FR-002: Валидация контракта — Must Have

IF контракт не парсится, пуст (`tasks: []`), содержит > 16 задач, дублирует `id`,
`id` задачи > 256 символов или содержит CR/LF, `instructions` > 32 000 символов,
`files` > 32 или содержит пустые строки, `maxWorkers` < 1, ИЛИ `contract` не проходит
валидацию атомика (не объект; owners/provides/requires ссылаются на неизвестные
задачи; owners с пустым путём; provides > 64 или с неверным kind; requires не
`{task, name}` с известной задачей и непустым name; checks > 16 или с пустым spec;
неверные типы полей; рендер контракта > 8000 знаков)
THE SYSTEM SHALL вернуть ошибку (`isError`) с `reason` и полем-нарушителем, не
запуская ни одного воркера; семантическая НЕСБУВАЕМОСТЬ контракта (чего он требует,
а задачи не дают) НЕ отказывается — уходит в warnings (философия атомика);
`title` без явного значения = humanised `id` (порт атомика)
SO THAT кривой вызов не сжигает токены, а контракт валидируется как в atomic-agent.

### FR-003: Ширина fan-out и клампы — Must Have

WHEN вызов называет `maxWorkers`
THE SYSTEM SHALL держать одновременно ≤ min(maxWorkers, tasks.length, maxParallel,
per-model cap) воркеров; WHEN не называет — использовать `config.workers`;
оставшиеся задачи — очередь FIFO
SO THAT параллелизм никогда не превышает физику машины и конфиг оператора.

### FR-004: Cap на модель — Must Have

THE SYSTEM SHALL держать ≤ 2 одновременно живых воркеров на одну модель при выборе
модели из ротации `workerModels`; модель выбирается round-robin с пропуском
«занятых»
SO THAT квоты провайдеров не штурмуются параллелизмом.

### FR-005: Порядок и полнота результатов — Must Have

THE SYSTEM SHALL возвращать результаты в порядке индексов задач независимо от
порядка завершения, с флагами клампа (значение + причина) и суммарным usage детей
SO THAT лид может сверить каждую задачу с её брифом и видит ограничения.

### FR-006: Структурный отчёт воркера — Must Have

THE SYSTEM SHALL запрашивать от каждого воркера отчёт строго по схеме:
`status (done|no_changes|failed|needs_orchestrator)`, `summary`, `filesChanged[]`,
`evidence[]`, `residualRisks[]`, опционально `replacedExistingFiles[]` и
`question` (обязателен при needs_orchestrator); `no_changes` — самодекларация
«завершил, ничего не менял» (паритет статуса атомика; там он выводится из фактов
записи — отклонение задокументировано в design TD-007)
SO THAT результаты машинно сверяемы и агрегируемы в таблицу.

### FR-007: Ретрай отчёта — Must Have

IF отчёт воркера не проходит валидацию схемы
THE SYSTEM SHALL ровно один раз запросить у того же воркера повторный отчёт с
указанием нарушенных полей; IF повторный провал — статус `failed` с пометкой
`schema-missing`
SO THAT работа на диске не пере-имплементируется из-за кривой формы отчёта.

### FR-008: Таймауты, бюджет и изоляция — Must Have

THE SYSTEM SHALL ограничивать каждого воркера `timeoutMs` задачи (кламп конфигом
`taskTimeoutMs`; потолок = 4 × базового — порт атомика `WORKER_BUDGET_CEILING_FACTOR`),
маппить `maxSteps` задачи в жёсткий бюджет тул-вызовов запроса (`toolBudget.hard`,
обязательное поле шва), при истечении локального дедлайна (timeout + 15s grace)
слать ребёнку `:cancel` и освобождать слот, а запрос создавать без тулов
делегирования (block-list)
SO THAT зависший воркер не держит fan-out, бюджет тулов честен, а рекурсия невозможна механически.

### FR-009: Деградация — Must Have

WHEN delegation-шов недоступен (нет шины событий) до запуска пула
THE SYSTEM SHALL вернуть лиду отказ «fusion недоступен — делай работу сам» без
запуска воркеров, с пометкой seamUnavailable
SO THAT лид падает обратно в обычный режим, а не ждёт вечно.
IF шов теряет доступность В СЕРЕДИНЕ fan-out (например, `unavailable_context` от
части детей)
THE SYSTEM SHALL вернуть частичные результаты: завершённые задачи как есть,
незавершённые — failed с ошибкой seam-unavailable.

### FR-010: Usage-агрегация — Must Have

THE SYSTEM SHALL суммировать usage всех детей из терминальных ответов шва
(authoritative; input/output/cacheRead/cacheWrite/turns/cost; usage прикладывается
к ЛЮБОМУ терминальному исходу, включая упавшие попытки failover — адаптер шва
не гейтит его по статусу, B-2-R5) и включать его в
result тула; usage из `:update`-снимков НЕ суммируется (кумулятивные снимки —
двойной счёт) и служит только живой диагностикой; отсутствие usage трактуется
как «неизвестно», не как 0; нулевые `toolCalls`/`durationMs` от шва (адаптер
ставит `?? 0`) означают «нет данных» — в usagePartial не участвуют (m3-R5)
SO THAT totals сессии точны, а barren-детектор не путает «0 шагов» и «нет данных»;
usage и turns суммируются по ВСЕМ попыткам задачи (включая failover-попытки);
ДЛЯ barren-детектора (F19, спека 003): при отсутствии терминального usage движок
использует последний `:update`-снимок `turns` ПОСЛЕДНЕЙ попытки (turnsObserved;
снимки кумулятивны в рамках одной попытки); оба отсутствуют — «неизвестно», не барен.

### FR-011: Подмена модели без потери работы (model-failover) — Must Have

WHEN задача завершается отказом, относимым к модели (`timed_out`, `interrupted`,
hostError с modelAttributable = true — единый критерий Q-002: структурный
providerDiagnostics.lastError.kind === "rate_limited" ИЛИ case-insensitive substring
текста ошибки 429/overload/rate-limit/quota)
THE SYSTEM SHALL пере-делегировать ТУ ЖЕ задачу другой модели из ротации с
continuation-брифом (исходные instructions + причина отказа + указание
«частичное состояние — на диске в scope files: проверь и доделай, не пере-делай»),
не более 2 подмен на задачу (3 запуска суммарно)
SO THAT сбой одной дешёвой ноги не убивает сделанную работу и не вызывает
ре-имплементацию.
IF другой модели с ёмкостью нет (в т.ч. единственная модель в ротации) — задача
немедленно failed с ИСХОДНОЙ причиной, вызов продолжается (отказ одной задачи — не
отказ вызова); `timeout`/`interrupted` НЕ исключают модель из ротации — исключение
только при подтверждённом квотном отказе (единый критерий — Q-002: структурный
`rate_limited` или текст ошибки 429/overload/rate-limit/quota).
НЕ покрывается: schema-missing (это FR-007, та же модель), needs_orchestrator
(терминален, Q-001), `invalid_request`/`tool_budget_exhausted` (ошибки контракта,
подмена не поможет), `cancelled` (решение оператора).

## Non-Functional Requirements

### NFR-001: Usability

- Таблица результата читаема без скролла: `id · status · summary · files`; причины
  клампа — отдельной строкой.

### NFR-002: Performance

- Fan-out из N задач при ширине W исполняется за ≈ ceil(N/W) волн; накладные
  расходы пула — < 100 мс на задачу.

### NFR-004: Security / Privacy

- Воркер-запросы несут block-list тулов делегирования; в бриф уходит только текст
  задачи и контракт, ничего из переписки лида.

### NFR-005: Reliability

- Отказ/таймаут одного воркера не влияет на остальные задачи вызова; клиент шва
  освобождает подписку (dispose) при любом исходе; частичные результаты возвращаются.

## Constraints

- Исполнение — delegation-шов pi-subagents (события request/response/update/cancel);
  совместимость с установленной версией проверяется smoke-тестом (version skew —
  риск R1 из плана).
- Расширение живёт в обычном Node-процессе pi: таймеры и Promise доступны.
- Модели воркеров — из реестра провайдеров pi (могут включать локальный
  llama-server через models.json).

## Decisions

### D-001: Шов вместо сырых процессов

**Decision:** воркеры = субагенты через delegation-шов pi-subagents.
**Reason:** fresh-контекст, структурные отчёты, usage, cancel — из коробки; путь уже
обкатан pi-autoresearch (council-delegation.ts).
**Source:** обсуждение сессии (v1→v3).
**Impacts:** FR-001, FR-006, FR-008, Constraints.

### D-002: Схема-отчёт вместо парсинга текста

**Decision:** `result: {kind:"structured", schema}` в запросе шва.
**Reason:** 0 отказов формы в смежных кампаниях; текстовый парсинг — главный класс
отказов.
**Source:** pi-agile отчётный контракт.
**Impacts:** FR-006, FR-007.

### D-003: Per-model cap = 2

**Decision:** не более 2 живых детей на модель.
**Reason:** правило оркестрации владельца против 429-штормов; ротация размазывает
квоты.
**Source:** обсуждение сессии.
**Impacts:** FR-004.

### D-004: Ретрай отчёта ровно один

**Decision:** schema-missing → 1 перезапрос → failed с пометкой.
**Reason:** перезапуск брифа реализации пере-имплементирует сделанное (урок pi-agile
report-repair); ретрай отчёта дёшев и безопасен.
**Source:** pi-agile, FR-007.
**Impacts:** FR-007.

### D-005: Кап задач на вызов = 16

**Decision:** `tasks` принимается 1..16, больше — отказ с советом дробить на волны.
**Reason:** порт atomic-agent (`MAX_DELEGATE_TASKS = 16`, константа с комментарием
«Sixteen, not eight» — кап поднят ими намеренно, тест прибит); волны с ревью между
ними — семантика режима, а не один мега-вызов.
**Source:** atomic-agent `delegate-args.ts` (исправлено после ревью R1: ранее ошибочно
указывалось 1..8).
**Impacts:** FR-002.

## Questions

### Q-001: Считать ли `needs_orchestrator` терминальным для задачи в этом вызове?

**Status:** answered
**Answer:** да — задача возвращается лиду со статусом; движок не перезапускает её
сам (перезапуск — решение лида, новый вызов).
**Decision:** влияет на FR-006 (статус) и Out of Scope (никаких авто-ретраев задач).

## Risks and Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Version skew API шва pi-subagents | High | Smoke-проверка при старте; честная деградация FR-009 |
| 429/квоты дешёвых моделей | Medium | FR-004 cap + ротация; отказ per-task, не вызова |

## Glossary

- **Лид:** фронтир-модель главной сессии; планирует, делегирует, ревьюит.
- **Воркер:** ephemeral fresh-субагент на дешёвой модели, исполняет одну задачу.
- **Fan-out:** один вызов `fusion_delegate` с пулом задач.
- **Шов:** delegation-события pi-subagents (request/response/update/cancel).
- **Continuation-бриф:** бриф повторного запуска той же задачи на другой модели
после модельного отказа (FR-011); непрерывность работы даёт состояние на диске.
- **Barren fan-out:** фан-аут, в котором воркеры исполнили 0 шагов (метрика F19,
  вне этой спеки).

### Q-002: Какие отказы считать «модельными» для подмены (FR-011)?

**Status:** answered
**Answer:** статусы `timed_out`, `interrupted` и hostError с признаками модельной
вины. Классификация: первичный структурный признак —
`providerDiagnostics.lastError.kind === "rate_limited"` (поле терминального ответа
шва); вторичный — текст ошибки (429/overload/rate-limit/quota). Отказы БЕЗ
подмены: schema-missing, needs_orchestrator, invalid_request, tool_budget_exhausted,
acceptance_failed, cancelled — подмена не чинит их причину; термин «контентный
отказ» далее не используется (n2-R5). Исключение модели из ротации до
конца вызова — ТОЛЬКО при подтверждённом квотном отказе; `timeout`/`interrupted`
модель не исключают.
**Decision:** FR-011.
