# Design: fusion-brief-english

## Context

Два текстовых шаблона образуют «языковую поверхность» брифа воркера (см.
proposal.md — Why):

- `guidance.ts` → `BEHAVIOUR_LINES`: поведенческие строки guidance-секции
  `### fusion`, которые расширение добавляет в system prompt лида на каждом
  `before_agent_start`. Сегодня языку полей там посвящено ничего.
- `briefs.ts` → `quoteOriginalRequest`: первая строка блока ORIGINAL REQUEST —
  метка, поясняющая роль цитаты запроса оператора. Тело цитаты механически
  дословно, у оператора оно обычно русское.

Владелец выбрал вариант «A+C» (2026-11-03): текстовое правило для лида +
пояснение в метке блока; без конфиг-флага, без гейта-отказа, без перевода.

## Goals / Non-Goals

**Goals:**

- Лид знает и выполняет правило «рабочие тексты полей задачи и контракта — на
  английском» независимо от языка запроса оператора.
- Воркер, не читающий язык оператора, понимает из метки блока, что цитата —
  контекст на языке оператора, а его задание самодостаточно и ниже.
- Изменение остаётся двумя правками шаблонного текста с тестами-пинами.

**Non-Goals:**

- Никакой валидации, детекции языка или отказа по языку (кириллица в полях
  остаётся валидной) — вариант B владельцем не выбран.
- Никакого машинного перевода (в т.ч. перевода ORIGINAL REQUEST) — вариант D
  отложен до живых наблюдений.
- Никакой новой настройки конфигурации (`briefLanguage` и т.п.).
- Отчёты воркеров, профили агентов, guidance о делегировании как таковом —
  не трогаются.

## Decisions

### D1. Guidance-строка: расширенная существующая строка против новой

Выбор: **новая строка в `BEHAVIOUR_LINES`** (а не дописывание существующей
строки про ORIGINAL REQUEST, и не отдельный подраздел).

Почему: правило адресовано лиду при написании полей задачи — это поведение
делегирования, а не механика цитаты. Существующая строка про ORIGINAL REQUEST
описывает, что делает расширение; новое правило — то, что должен делать лид.
Отдельный подраздел — избыточно: одна строка, все секции уже плоские.
Порядок: сразу после строки про роли (`role`) — правило про текст задачи
логически продолжает правило о составе задачи.

Черновик строки (текст финализируется при реализации, пин-тест фиксирует
итоговый вид):

> Write every task's `instructions`, `title`, `deliverable` and any
> `contract.provides[].shape` in English, whatever language the operator
> used — worker models may not read it. Keep paths, file names, identifiers,
> commands and other literal strings as-is.

Альтернатива «дополнить строку про ORIGINAL REQUEST» отклонена: строка и так
длинная, и смешение двух субъектов (расширение-механика vs обязательство
лида) ухудшает читаемость.

### D2. Метка блока ORIGINAL REQUEST: дополнение существующей метки

Выбор: **дополнить первую строку метки** в `quoteOriginalRequest` (не вторая
строка, не сноска в конце блока).

Сегодняшняя метка: «ORIGINAL REQUEST — context only; your task is below. This
is the operator's job…». Дополнение добавляет к первой строке: цитата
приведена на языке оператора; воркер может не знать этого языка; задача
изложена ниже на английском и самодостаточна — всё нужное рестейтовано в
TASK.

Почему первая строка: это единственное место, которое воркер читает до
цитаты; пометка о языке до тела цитаты — стандартная форма оговорки.
Сноска в конце — после 16K символов непонятного текста, воркер мог уже
«споткнуться». Сегмент-обёртка `<notr>` не используется: расширение не знает
языка модели, Markdown-обёртки в Task-провайдерах не стандартизированы, а
оговорка словами читается всеми.

Текст метки финализируется при реализации; пин-тест фиксирует вид.
Бюджет обрезки цитаты (16 000) не меняется: дополнение — одна строка вне
тела цитаты.

### D3. Тесты: пины на фразы против структурных проверок

Выбор: **пины на ключевые фразы** (как в существующих `guidance.test.ts` /
`briefs.test.ts`), а не счётчик строк/слов.

Почему: правило текстовое; его наблюдаемая единица — присутствие ключевых
фраз в результирующих строках: «English» + перечень полей (guidance),
«operator's language» / «English» / «self-contained» (метка блока).
Структурные проверки (длина, количество строк) хрупки и не проверяют смысл.
Существующие пины метки (`briefs.test.ts` ~L140, `fanout-e2e.test.ts` ~L234)
проверяют префикс «ORIGINAL REQUEST — context only; your task is below»
через `toContain` — дополнение строки ХВОСТОМ метки их не ломает; их сознательно
не трогаем. Пин «keeps the lead's language in the instructions untouched»
(`briefs.test.ts`) уже закрепляет, что кириллица в полях проходит насквозь —
он остаётся зелёным без правок.

### D4. README

Одна строка в раздел про делегирование: брифы пишутся на английском; цитата
запроса остаётся на языке оператора и помечена.

## Risks / Trade-offs

- [Лид игнорирует текстовое правило (нет гейта)] → Митигация: правило в
  guidance-секции, которую лид читает на каждом старте; фраза короткая и
  повелительная; при живых наблюдениях можно вернуться к варианту B
  (валидация-отказ) как к следующему шагу — спека `brief-language` явно
  запрещает гейт СЕЙЧАС, но не запрещает новое изменение потом.
- [Метка блока удлинилась — рост контекста воркера] → одна строка (~200
  символов) на бриф; пренебрежимо на фоне бюджета цитаты 16K.
- [Владелец пишет операторский запрос не на русском, а на другом языке] →
  правило не привязано к русскому: «whatever language the operator used»;
  метка говорит «the operator's language» без конкретики.
- [Фразы-пины хрупки к переформулировке] → осознанный выбор: пин
  обновляется вместе с текстом в одном PR; потеря пина при правке текста —
  желаемое поведение (заставляет обновить оба).

## Migration Plan

Два коммита не нужны: изменение атомарно, обратносовместимо, работает со
следующего `before_agent_start` после пересборки/перезапуска pi. Откат —
revert одного коммита.
