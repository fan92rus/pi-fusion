# Proposal: fusion-project-config

> Автор — lead сессии. Язык артефактов — ru (конвенция config.yaml).
> Решения владельца (2026-11-05, сессия): (1) проектный конфиг — `.pi/fusion.json`
> в корне проекта; (2) чтение — послойное на уровне полей: локальное значение
> заменяет глобальное БЕЗ суммирования, включая блокировки инструментов;
> (3) выбор цели записи — переключатель global/local ВНУТРИ интерактивного
> `/fusion config`; подкоманды-ярлыки пишут по правилам design D4.

## Why

Сегодня вся конфигурация fusion — один глобальный файл
`~/.pi/agent/fusion.json`. Владелец работает в разных проектах с разными
потребностями: в одном нужны другие модели ротации (бесплатные локальные), в
другом — другой таймаут или шире/уже гейты лида. Сейчас это ручная правка
одного файла с риском «поставил под проект — сломал всем» и никакого способа
закрепить настройки за проектом (в git не положишь). pi имеет конвенцию
проектных настроек `.pi/` (`.pi/settings.json`, `.pi/mcp.json`), поэтому
естественная форма — проектный `.pi/fusion.json`, накрывающий глобальные
поля.

## What Changes

- Новый проектный файл конфигурации `.pi/fusion.json` (в корне рабочего
  каталога проекта, по конвенции `.pi/` из документации pi).
- Послойное чтение per-field: эффективное значение каждого поля =
  валидное значение из `.pi/fusion.json`, если ключ задан; иначе глобальное;
  иначе дизайн-дефолт. Невалидное локальное значение = наследование (warn).
  Списковые поля (`workerModels`, `blockedTools`, `leadBlockedTools`) —
  обычные поля: локальный список заменяет глобальный целиком, БЕЗ
  объединения (решение владельца); явный пустой список — валидное
  переопределение.
- Интерактивное меню `/fusion config` получает переключатель конфигурации
  global ↔ local: нулевой экран выбора; выбранный слой определяет, какой
  файл читают и правят экраны. Local-режим показывает источник каждого поля
  (local/global/default); правка сохраняется сразу после каждого изменения
  (как сегодня), но в local — дельтой только изменённого поля;
  переопределение наследуемого поля — с явным подтверждающим шагом; сброс
  переопределения удаляет локальный ключ, опустевший файл удаляется.
- Подкоманды-ярлыки (`/fusion workers|model|timeout`) пишут по правилу
  design D4: существующий `.pi/fusion.json` → дельта в него; отсутствие
  файла → глобальный полный снапшот, проектный файл не создаётся.
- `/fusion status` показывает источник каждого поля (local/global/default).
- Гейт лида (`leadBlockedTools`) читается свежо при каждом вызове —
  локальное переопределение блокировок подействует без перезапуска.
- Чтение остаётся свежим при каждом вызове (как сегодня): ручная правка
  файлов применяется без перезапуска.

## Capabilities

### New Capabilities

- `project-config`: послойная конфигурация fusion: проектный файл
  `.pi/fusion.json`, правила наложения на глобальный (per-field замена без
  суммирования), выбор цели записи в `/fusion config`, отображение
  происхождения полей в `/fusion status`.

(нет — живых главных спек нет; см. proposal fusion-brief-english)

## Impact

- Код: `config.ts` (presence-aware чтение локального слоя, origins, дельта-
  запись/сброс), `commands.ts` (слоеные deps-операции вместо
  loadConfig/persistConfig; status с источниками; ярлыки по D4),
  `config-ui.ts` (нулевой экран-переключатель, local-режим с индикацией
  источника, per-edit дельта-запись, сброс переопределения), `index.ts`
  (прокидывание projectConfigDir; гейт лида на свежем чтении blockedTools),
  `restrictions.ts` (blockedTools как геттер), `config-bridge.ts`
  (делегирование слоёной функции).
- Тесты: `config.test.ts`, `command.test.ts`, `config-ui.test.ts`,
  `restrictions.test.ts`, `scaffold.test.ts`/`tool-wiring.test.ts`
  (привязка cwd), новые кейсы наложения, приоритета, ярлыков и сброса.
- README: раздел про слоёную конфигурацию (включая доверие: файл в репо
  меняет конфигурацию каждому клону — не коммитьте файл, которому не
  доверяете).
- Не меняет: сессионную активацию (session-state), пул, seam, профили,
  схему `fusion_delegate`.
- Ограничение: расширение читает `.pi/fusion.json` само, независимо от
  механизма project trust pi; домен доверия — репозиторий (тот же каталог
  `.pi/`, из которого pi грузит и расширения). Клонирование репо с файлом
  меняет конфиг fusion проекта; README фиксирует правило доверия
  (design R5).
