# Design: fusion-project-config

> rev.4 — закрыты блокер и мажоры раунда 3: запись отказывает и в
> не-объект JSON (асимметрия с чтением снята), убрано противоречие
> «read-only vs переопределение с confirm», presence-aware чтение определено
> для ОБОИХ слоёв (origins global/default различимы), unit-тесты отказа
> записи и копирайт leadBlockedTools добавлены в задачи. rev.3 — закрыты
> блокеры раунда 2; rev.2 — раунда 1.

## Context

Вся конфигурация fusion сегодня — один глобальный файл (config.ts
`loadFusionConfig`, читается свежо при каждом вызове; `/fusion`-команды и
меню `/fusion config` пишут атомарно через `persistFusionConfig` — полный
канонический снапшот; меню персистит после КАЖДОЙ правки, без save-on-exit).
`FusionCommandDeps` даёт командам `loadConfig()/persistConfig(next)`; гейт
лида получает `blockedTools` ОДИН раз на загрузке расширения
(index.ts `startup.leadBlockedTools`). Проектного слоя нет. pi имеет
конвенцию `.pi/` для проектных настроек (`.pi/settings.json`,
`.pi/mcp.json`). Владелец утвердил 2026-11-05: `.pi/fusion.json`, per-field
замена без суммирования (включая блокировки), переключатель global/local
внутри `/fusion config`.

## Goals / Non-Goals

**Goals:**

- Эффективный конфиг = глобальные поля, переопределённые валидными локальными
  per-field; списки заменяются целиком.
- Переключатель слоя в меню; ярлыки — по правилу «пишем туда, откуда пришло»;
  происхождение поля видно в меню и `/fusion status`.
- Форма полей, границы, атомарная запись, свежее чтение — без изменений.

**Non-Goals:**

- Никакого мёрджа/суммирования списков (решение владельца).
- Никаких CLI-флагов/подкоманд выбора слоя (только меню).
- Активация остаётся сессионной; поля `enabled` нет ни в одном слое.
- Project-trust не реализуется: расширение читает только cwd, конфиг не
  исполняет код (см. R5 — доверие на уровне репозитория).

## Decisions

### D1. Чтение локального слоя: presence-aware парсер

Существующий `readFields` НЕ годится для локального слоя: он возвращает
полный `FusionConfig`, где невалидное поле неотличимо от отсутствующего
(оба → дефолт), а нам нужно именно «наследовать глобальное». Поэтому новый
presence-aware ридер применяется к ОБОИМ слоям (одна реализация, разные
пути/варны):

- глобальный слой: тот же парсер по `~/.pi/agent/fusion.json` — ключ есть и
  валиден → источник `global`; нет/невалиден → `default` (существующий warn
  на невалидное глобальное поле сохраняется); 
- локальный слой: `<cwd>/.pi/fusion.json`; ENOENT → слой пуст, молча;
  непарсящийся JSON или не-объект (массив/null/скаляр) → слой пуст целиком,
  один warn; для каждого поля отдельно: ключа нет → «наследуется»; ключ
  есть и валиден (те же провайдеры типов и `FUSION_CONFIG_BOUNDS`, что у
  глобального) → переопределение (`origin: local`); ключ есть, но значение
  невалидно → «наследуется» + warn с именем поля (изоляция полей);
- `enabled` в любом слое → single-warn про retired, поле игнорируется;
- явный пустой список (`[]`) — валидное переопределение (наличие ключа
  различимо): локальный `workerModels: []` выключает fan-out в проекте,
  не трогая глобальную ротацию.

Эффективный конфиг: дефолты → валидные глобальные значения → валидные
локальные переопределения; origins (`"local" | "global" | "default"`)
вычисляются в том же проходе. `default` = поля нет (или невалидно) ни в
одном файле.

### D2. Происхождение полей: `FieldOrigins`

`type FieldOrigins = { [K in keyof FusionConfig]: "local" | "global" | "default" }`.
Один источник правды (`loadEffectiveConfig(globalPath, projectDir)` возвращает
`{ config, origins }`) для `/fusion status`, меню и тестов. Внутрь
`FusionConfig` origins не вмешиваются — тип уходит в пул как сегодня.

### D3. Запись: два API, дельта-запись для local

- `persistFusionConfig(next)` — глобальный слой, полный канонический снапшот,
  без изменений.
- `persistProjectFusionDelta(delta: Partial<FusionConfig>, projectDir)` —
  читает СЫРОЙ JSON локального файла (если есть), мёрджит ТОЛЬКО ключи
  дельты, сохраняет неизвестные ключи как есть, атомарный tmp+rename.
  Никакой канонической досыпки всех полей — в файле живут только
  переопределения (и неизвестные ключи, если их туда wrote человек).
  Если файл существует, но непарсится как JSON или не является объектом
  (массив/null/скаляр) — запись ОТКАЗЫВАЕТ с понятной ошибкой (путь +
  причина); молча перезаписать человеческую правку нельзя (данные в битом
  файле дороже удобства записи) — та же граница «битости», что у чтения
  (D1). Создание нового файла (отсутствующего) — нормально.
- `clearProjectFusionOverride(key, projectDir)` — удаляет ключ из сырого
  JSON (битый файл — тот же отказ); когда известных полей не осталось и
  объект пуст — файл удаляется (пустой `{}` не сохраняется: отсутствие
  файла — честный маркер «проект ничего не переопределяет», на него
  завязано D4). Неизвестные ключи при очистке сохраняются (файл удаляется
  только когда пуст совсем).

### D4. Ярлыки: «пишем туда, откуда пришло»

`/fusion workers|model|timeout`: существует `<cwd>/.pi/fusion.json` (даже
пустой или только с неизвестными ключами) → дельта в него; иначе → полный
снапшот в глобальный. Обоснование: существующий локальный файл = намерение
проекта владеть конфигом; ярлык, пишущий глобально поверх существующего
локального, создал бы правку, которую локаль сразу перекроет (невидимое
изменение — худший исход). Создание локального файла ярлыком — нет: слишком
много магии, для этого есть меню (D5), которое спрашивает явно.

### D5. Deps-шов и меню: слоеные операции вместо одного persistConfig

`FusionCommandDeps` расширяется (вместо одного `loadConfig/persistConfig`):

- `loadEffective(): FusionConfig` и `getOrigins(): FieldOrigins` —
  эффективность и происхождение (status, главные экраны);
- `loadGlobal(): FusionConfig`, `persistGlobal(next)` — global-режим меню;
- `projectConfigExists(): boolean`;
- `persistProjectDelta(delta: Partial<FusionConfig>)`,
  `clearProjectOverride(key: keyof FusionConfig)` — local-режим меню.

Существующие сигнатуры `loadConfig/persistConfig` заменяются на этот набор
(точечный рефактор вызовов; редакторы меню больше НЕ делают
`{...loadConfig(), key}` — в global-режиме пишут через `persistGlobal`,
в local — через `persistProjectDelta`).

Меню: нулевой экран — выбор `Global (~/.pi/agent/fusion.json)` /
`Local (.pi/fusion.json — есть/отсутствует)`; дефолт при входе: local, если
файл существует, иначе global. Global-режим = сегодняшние экраны, привязанные
к `loadGlobal/persistGlobal`. Local-режим: список полей с эффективным
значением и суффиксом источника (`[local]`/`[global]`/`[default]`);
правка поля → НЕМЕДЛЕННАЯ `persistProjectDelta({key: value})` (per-edit
персистентность сохраняется — save-on-exit не вводится); правка
наследуемого (global/default) поля в local-режиме требует явного шага
«переопределить здесь» (confirm), чтобы дельта не создавалась мимоходом;
сброс переопределения → `clearProjectOverride(key)`. Переключение слоя
ничего не пишет.

### D6. `FusionExtensionOptions` и cwd

`FusionExtensionOptions` расширяется: `projectConfigDir?: string` (тесты;
продакшн — `process.cwd()` на момент ЧТЕНИЯ, т.е. внутри
`loadEffectiveConfig`, а не один раз на загрузке: расширение должно видеть
файл, появившийся после старта). Слой действует на каталог запуска pi — как
`.pi/settings.json` самого pi.

### D7. config-bridge.ts и guidance

Read-only мост делегирует `loadEffectiveConfig` (усечённо: без origins),
чтобы тесты моста и продакшн-чтение не расходились. Guidance facts
(index.ts `registerFusionGuidance`) читают ЭФФЕКТИВНЫЙ конфиг тем же
путём — рабочие модели и потолки в секции `### fusion` соответствуют
локальным переопределениям (задача 2.2).

### D8. `/fusion status`

Выводит каждое поле с суффиксом источника: `workers: 8 [local]`,
`models: A, B [global]`, `timeout: 600000 [default]`. Источник — из
`getOrigins()`.

### D9. Гейт лида: свежее чтение blockedTools

Сегодня `registerLeadRestrictions(pi, { blockedTools: startup.leadBlockedTools })`
привязывает список один раз на загрузке, а restrictions.ts строит из него
Set блокировок один раз при регистрации — локальное переопределение
`leadBlockedTools` не подействовало бы никогда. Deps гейта меняются:
`blockedTools: () => string[]` — restrictions.ts вызывает геттер и строит
Set заново при каждой проверке (стоимость пренебрежима: проверка — один
includes); index.ts биндит на эффективный конфиг. Задача 2.2 включает этот
рефактор и его тесты.

## Risks / Trade-offs

- [Оператор ожидает мёрдж списков, получает замену] → решение владельца;
  суффиксы источника в status/menu делают активный слой явным; README
  проговаривает замену целиком.
- [Ярлык молча создаёт локальное переопределение при существующем файле] →
  видимое поведение: status сразу показывает `[local]` у изменённого поля.
- [Закоммиченный .pi/fusion.json ослабляет гейты для каждого клона] → R5
  (ниже): доверие на уровне репозитория, документировано в README.
- [Два файла — рассинхрон при ручной правке] → свежее чтение при каждом
  вызове; битые значения warn + наследуются.
- [R5: локальный `leadBlockedTools: []` снимает F19-блокировки лида;
  локальный `requireApproval: false` — подтверждения] → осознанный trade-off
  владельца. Честно: pi НЕ гейтит `.pi/fusion.json` своим project trust
  (список доверенных путей pi его не включает — расширение читает файл
  само, как только pi запущен в каталоге). Домен доверия здесь — сам
  репозиторий: клонирование чужого репо с .pi/fusion.json меняет конфиг
  fusion в этом проекте (но не глобально и не исполняет код — в отличие от
  .pi/extensions/, которые pi грузит из того же каталога). README фиксирует:
  не коммитьте файл, которому не доверяете, и пересматривайте его при
  клонировании чужих репо.
- [Пустой локальный файл после сбросов] → удаляется (D3), D4 остаётся
  честным.
- [Неизвестные ключи в локальном файле] → сохраняются при дельта-записи,
  игнорируются при чтении (warn не спамим: один warn на файл за процесс).

## Migration Plan

Обратносовместимо: без `.pi/fusion.json` поведение байт-в-байт сегодняшнее
(кроме рефактора deps-шва и гейта — внутренние сигнатуры, наблюдаемое
поведение то же). Откат — revert коммита.
