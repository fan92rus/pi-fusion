## 1. Executive Summary

Спека добавляет к существующему fan-out'у (спека 001) четыре ролевых профиля
`worker / scout / researcher / reviewer` на базе pi-subagents и два точечных
исключения из полного блока мутирующих тулов лида (F19): штатные `write`/`edit`
внутри реальной цели `openspec/` проекта (граница — `realpath`, даже вне корня проекта) и доверительный полнофункциональный `perl` через
`bash`. Роли переиспользуют весь работающий конвейер — схему контракта, шов,
пул, расписание, окно rate-limit, ретрай отчёта, деградацию — меняя только
(а) нормализацию новой опциональной роли в валидаторе, (б) выбор
агент-профиля/схемы отчёта/блок-листа тулов в шве, (в) манифест установщика
профилей, (г) условные исключения в lead-гейте с явной рамкой «проверяемая
граница, а не песочница». Роль по умолчанию — `worker`: существующие вызовы
без `role` ведут себя побайтово как сегодня.

### Поток данных роли

```
fusion_delegate(tasks[].role?)
  → contract/validate.ts: role нормализована (дефолт worker), неизвестная — refusal
  → pool/fanout.ts: ширина/расписание/окно БЕЗ ИЗМЕНЕНИЙ; в launch() роль идёт в client.run
  → seam/client.ts: request { agent: fusion-<role>, model: <из ротации>,
        toolBudget.block: <по роли>, result.schema: <ролевая схема отчёта> }
  → pi-subagents: резолвит агент-профиль fusion-<role> (researcher — вариант
    по составу `researcherWeb`, §4.9.3; docs/agents.md «Where agents live»)
  → отчёт: ролевая схема (общий конверт) → schemaFailed? → report/retry.ts (та же роль, тот же слот)
  → TaskResult (конверт + опциональные ролевые поля) → FanoutResult → лид
```

## 4. Роли

### 4.1 Схема вызова

`FusionTaskSchema` (types.ts:55-91) получает одно опциональное поле:

```ts
role: Type.Optional(Type.Union([
  Type.Literal("worker"), Type.Literal("scout"),
  Type.Literal("researcher"), Type.Literal("reviewer"),
])),
```

`additionalProperties: false` сохраняется; строка роли длиной/регистром не
нормализуется — точные литералы (`"Worker"` — неизвестная роль).

### 4.2 Валидатор (contract/validate.ts)

- `TASK_KEYS` (:178) дополняется `"role"`.
- `parseTask` читает роль и **всегда** кладёт конкретное значение в
  `ValidatedTask` (по образцу нормализации `title`,
  contract/validate.ts:199-203): отсутствует/учтено →
  `"worker"`. Даунстрим (брифы, пул, шов, ретрай) опциональность не видит.
- Неизвестное значение — `refuse("role must be one of worker, scout, researcher, reviewer", "tasks[i].role")`
  — тот же механизм `Refusal` (:71-79), тот же формат `{ ok: false, error: { reason, offender } }`
  из `validateFusionCall` (:584), тот же рендер отказа в index.ts:101-105.
- Отказ происходит **до** `runFanout` (index.ts:111) — ни один воркер не стартует (семантика FR-001).

### 4.3 Fanout (pool/fanout.ts) — инварианты сохраняются

Без изменений и поэтому переносимы на любую роль: цепочка ширины
`planFanoutWidth` (:99), `PER_MODEL_CAP` (:43), `WINDOW_STREAK_LIMIT` (:41),
FIFO-расписание `dispatch()` (:430), окно rate-limit (`accountWindow` :337),
дренаж (`drainQueue`/`excludeModel`), Esc-обработка (`onAbort` :446,
`cancelAllPending` :454), баррен-
счётчик лида (restrictions.ts:40 — считает fan-out'ы, роли ему безразличны).
Единственная правка: `launch()` (:399) добавляет `role: task.role` в
`client.run(...)`; `settle()` передаёт роль в ретрай. Ролевые задачи попадают
в общую очередь — ротация моделей, клампы и `ClampRow` не знают о ролях.

### 4.4 Профили агентов

Файлы в `extensions/pi-fusion/agents/`, устанавливаются установщиком в
`~/.pi/agent/agents/` (worker-install.ts:35-37), резолвятся pi-subagents по
имени из шва (docs/agents.md «Where agents live», приоритет builtin < package < user < project (agents.md:17-24; проектный
уровень `.pi/agents/` при доверии к проекту перекрывает `fusion-*`,
agents.md:34) — руководство оператора может переопределить профиль, это
документированное свойство, §7, §9.1).

| Профиль | frontmatter `tools` | seam `toolBudget.block` | Смысл инструкции |
|---------|--------------------|--------------------------|------------------|
| `fusion-worker` (существует, fusion-worker.md:6) | `read, grep, find, ls, bash, edit, write` | `["fusion_delegate","subagent","codemode"]` — без изменений (client.ts:28) | реализация + свои проверки в `evidence` |
| `fusion-scout` | `read, grep, find, ls` | база + `["edit","write","bash"]` | разведка кода: файлы, точки входа, потоки данных, риски; источники как `file:line` |
| `fusion-researcher` + варианты `-web`/`-codex`/`-both` (§4.9.3) | `read, grep, find, ls`; веб-имена — ровно по составу `researcherWeb` из конфига (§4.9.3) | база + `["edit","write","bash"]` | веб-исследование с источниками и ссылками; неизвестное — помечать; состав без веба — отчёт с `unknowns`; несоответствие состава окружению — preflight `failed` (§4.9) |
| `fusion-reviewer` | `read, grep, find, ls, bash` | база + `["edit","write"]` | ревью против задачи/плана: находки + **собственные** прогоны проверок с выводом |

Общее для новых профилей (паритет с fusion-worker.md:4-10): `systemPromptMode:
replace`, `inheritProjectContext: true`, `inheritSkills: false`,
`defaultContext: fresh`, **без** `model:`/`thinking:` и без
`allowNestedSubagents`. В каждой инструкции: один вызов шва — один сеанс, без
истории и канала уточнений; запрет трогать git и bd (как fusion-worker.md:17-21);
терминальный ответ — ровно JSON-отчёт ролевой схемы (§4.8).

Механическое сужение двоякое: allowlist в профиле (pi-subagents отдаёт ребёнку
только перечисленное, docs/agents.md «Tool and extension selection») и
`toolBudget.block` шва. **Это сужение, не изоляция**: у reviewer есть `bash` —
bash пишет файлы так же, как `write`; требования (FR-003) прямо фиксируют, что
наличие shell не считается гарантией отсутствия записи. Отсутствие `edit`/
`write` в allowlist`e отрезает *прямые* правки, остальное — инструкция и доверие (§9).

### 4.5 Retry отчёта (report/retry.ts)

Ретрай не знает о роли, кроме схемы: `runReportRetry` (:207) получает `role`
в `SchemaRetryRequest`, шов для корректива собирает ту же ролевую схему;
`nodeId` = `<task>#a2` (:213, без изменений), `RETRY_TIMEOUT_MS` = 120 с (:29),
`RETRY_ATTEMPT` = 2 (:32), слот модели удержан вызывающим (TD-004 спеки 001).
Второй `schemaFailed` — терминальный `schema-missing`, окно не растёт (Q-002) —
для всех ролей одинаково.

**Корректирующая попытка выполняется свежим ребёнком (`context: "fresh"`,
client.ts:316) и получает сегодня ровно один payload — текст корректива
(retry.ts:214); ролевая схема сама факты не восстанавливает. Сегодня шов
в `schemaFailed` несёт только `violatedFields`/`usage` (тип `SeamOutcome`,
client.ts:99): значение `result.value` вычисляется локально в ветке
client.ts:239-244, но через шов не проходит.** Свежий агент без контекста не
знает, что было сделано, и не может честно исправить отчёт — разрыв доставки,
исправляется так:

1. **Бриф задачи — контекст переоформления.** `SchemaRetryRequest` дополняется
   полем с брифом задачи (тот же рендер, что у первой попытки); передача
   проверяема: вызывающий `settle` имеет `ValidatedTask` в области видимости
   (fanout.ts:363). Это сознательное и обоснованное отклонение от TD-004
   спеки 001 (001 design.md:649): та отвергает «ре-запуск брифа» как
   **пере-имплементацию** — повторное выполнение работы. Здесь бриф работу
   не запускает: это report-only контекст переоформления уже сделанной
   работы (пп. 4) — без брифа свежий ребёнок не смог бы честно переоформить
   отчёт, а повторная реализация запрещена.
2. **Отвергнутый ответ — значение, виденное швом (B3).**
   `schemaFailed`-ветка внутреннего типа `SeamOutcome` (client.ts:99 — это
   не wire-контракт: наружу шов отдаёт только итоговый результат)
   расширяется опциональным полем со значением отвергнутого ответа. Значение
   берётся ровно там, где оно уже вычислено (client.ts:239-244) —
   расширение внутреннего типа шва, не реконструкция. Сериализация:
   `result.value` — разобранный объект, не сырой текст; в корректив значение
   идёт как `JSON.stringify(value)` (UTF-8). Поле ограничено по размеру:
   жёсткий лимит 16 000 символов, при превышении — обрезка с явной пометкой
   усечения. В коррективе ответ передаётся как JSON «отвергнутой попытки» с
   пометкой
   «отчёт отклонён по схеме, поля: …». Доставка закрепляется тестом: значение
   доходит от `SeamOutcome` до `runReportRetry` и попадает в корректив (§11).
3. **Честная недоступность.** Если хост отказал до движка (значения нет,
   `violatedFields` = []) — прошлого ответа не существует; корректив прямо
   говорит «предыдущий ответ недоступен». Ребёнок не изображает работу,
   которой не видел.
4. **Корректив — report-only (B4, решение оператора).** Контракт «Реализацию
   не повторять» (retry.ts:41-47) сохраняется и усиливается: ребёнок
   **только** переоформляет отчёт по ролевой схеме из переданного контекста
   (бриф + отвергнутый ответ при наличии). Повторная реализация, новые прогоны
   проверок и выдуманные `sources`/`checksRun`/`filesChanged` запрещены:
   поля, не подтверждаемые переданным контекстом, остаются пустыми,
   невосполнимые пробелы честно фиксируются в `residualRisks`/`unknowns`
   (по роли). Это снимает противоречие «переделывает работу по брифу»:
   повторная реализация на уже изменённом дереве давала бы двойные записи и
   выдуманные доказательства. FR-007 не меняется: ретрай остаётся второй
   попыткой **отчёта**, не работы (см. §8).

Сигнатура `SchemaRetryRequest` меняется (новые поля), а текст
`correctiveRequest` обновляется до report-only формулировки с вариантами
«прошлый ответ приложен / недоступен» — точечные расширения; пины спеки 001
на текст корректива обновляются в tasks.

### 4.6 Установка профилей (worker-install.ts)

Механика существующего установщика сохраняется: idempotent-копия, ключ — строка
`version:` во frontmatter (parseAgentVersion :61), исходы `installed|updated|current`
(:66), отсутствие/нечитаемость цели → запись (:91-105). Обобщение:

- `FUSION_ROLE_PROFILES`: манифест записей `{ name, filename, version }` —
  worker, scout, reviewer и 4 варианта researcher по составам `researcherWeb`
  (§4.9.3); у каждой роли/варианта свой `FUSION_<ROLE>_AGENT_VERSION` (воркер —
  существующий `FUSION_WORKER_AGENT_VERSION` = "1", worker-install.ts:27; bump
  каждой роли независимый).
- `installFusionWorkerAgent` (:85) сохраняет сигнатуру и поведение (совместимость
  с tests и командой); добавляется `installFusionRoleAgents(options)` = проход по
  манифесту, возвращающий `Array<InstallWorkerAgentResult & { name }>`.
- `/fusion on` и `/fusion config` проверяют **все** профили и нотифицируют
  построчно (например, `fusion-scout: installed @
  ~/.pi/agent/agents/fusion-scout.md`).
- **Подключение к фактическому командному пути (B6).** Сегодня `turnFusion`
  вызывает установщик только когда `agentInstalled()` = false
  (commands.ts:206-210), где `agentInstalled` = `existsSync` одного
  worker-файла (index.ts:224), а production-`installAgent` привязан только к
  `installFusionWorkerAgent` (index.ts:218-228). Следствия: существующий, но
  устаревший профиль не обновляется никогда — исход `updated` из командного
  пути недостижим; проверка «все существуют» устаревание не видит. Исправление:
  `FusionCommandDeps` дополняется `roleProfileStatuses()` — по манифесту
  `FUSION_ROLE_PROFILES`: цель отсутствует → `absent`, строка `version:` в целевом файле ≠
  манифесту → `stale`, совпадает → `current` — и `installRoleAgents()`;
  `turnFusion` и путь `/fusion config` вызывают установку при любом
  `absent`/`stale` и нотифицируют **фактический** исход по каждому профилю
  (`installed`/`updated`/`current`). «Все профили на месте» = все `current`,
  а не existsSync.
- **Статус и старт (FR-006).** `showStatus` (commands.ts:214-231, строка
  агента :221) сегодня
  печатает только `agent fusion-worker` — дополняется построчным статусом всех
  профилей (`absent`/`stale`/`current`). Обновление профилей при старте сессии
  **не** выполняется — сознательно: версии проверяют только командные пути
  `/fusion on` и `/fusion config`; при уже включённом fusion устаревший профиль
  остаётся до ручного запуска команды, но его состояние видно в `showStatus` —
  тихой рассинхронизации нет.
- Наблюдаемость отсутствия профиля (FR-006): если профиль снесён вручную, шов
  отвечает ошибкой резолва агента → задача `failed` с `host:<код>` (§4.10);
  тихого фолбэка на worker нет — специально (TD-02).

### 4.7 Модель (FR-002, D-001)

Отдельного выбора модели по роли нет и не появляется:

- шов передаёт `model` из ротации `config.workerModels` — тот же путь, что
  сегодня (client.ts:318 `model: req.model`); выбор модели в пуле — round-robin
  `pickModel` (fanout.ts:304) — роли не видит;
- файлы ролей **не** пинают `model:`/`thinking:`: per-run `model` из шва и так
  сильнее frontmatter (pi-subagents docs/models.md: «per-run override → … →
  agent frontmatter model»), но отсутствие пина устраняет сам вопрос;
- функциональность не требует второй модели: ревьюер работает на той же
  ротации, что воркер (операторская установка — одна модель).

### 4.8 Структурированные отчёты (FR-002)

Общий конверт остаётся `WorkerReportSchema` (report/schema.ts:24-57, types.ts:146):
`status` (4 литерала), `summary`, `filesChanged`, `evidence`, `residualRisks`,
`replacedExistingFiles?`, `question?` + if/then «needs_orchestrator ⇒ question»
(report/schema.ts:51-56). Правило if/then и CAVEAT про TypeBox 0.34
(report/schema.ts:12) переиспользуются всеми ролями без изменений.

Ролевые схемы = конверт + свои поля (`additionalProperties: false`):

| Роль | Доп. поля | Семантика |
|------|-----------|-----------|
| scout | `sources: string[]` | источники в коде, каждый как `path:line` (+1 строка что там) |
| researcher | `sources: string[]`, `unknowns: string[]` | ссылки/источники; `unknowns` — что не удалось проверить; незаполненное неизвестное в `sources` не изображается |
| reviewer | `findings: string[]`, `checksRun: string[]`, `verdict: "pass"\|"fail"` | находки; команды и решающий вывод **собственных** прогонов; вердикт |

`TaskResultSchema` (types.ts:184) дополняется теми же **опциональными** полями
(`sources?`, `unknowns?`, `findings?`, `checksRun?`, `verdict?`):
additive-изменение wire-формы. Копируют их при наличии **оба** сборщика
финальной строки: `resultFromOutcome` (fanout.ts:189) и `resultFromRetryOutcome`
(report/retry.ts:126-145) — ретрай собирает результат отдельно от первой
попытки, и без правки второго ролевые поля после успешного корректива
терялись бы (B3). Отчёт scout/researcher естественно несёт `filesChanged: []`.
Маппинг в текстовую таблицу лида (result.ts `renderFanoutText`) добавляет
ролевые поля в строку задачи; обязательный тест — полный путь
«ролевой отчёт → schemaFailed → ретрай с ролевыми полями → `renderFanoutText`»
(§4.11).

### 4.9 Веб-инструменты (researcher, FR-003)

Честность обеспечивается двумя независимыми механизмами (пп. 1 и 5 —
механический и инструкционный), и **ни один из них не
пытается угадать доступность сети заранее**; пп. 2-4 фиксируют доказанное
по коду провайдеров, переносимую политику составов и недоказанное:

1. **Механический (хост) — доказанная часть.** Делегатские дети — foreground:
   ambient-расширения у них не грузятся (agents.md:551-553); pi-subagents
   перед первым ходом ребёнка сверяет каждый явный тул с финальным реестром и
   **валит запуск с именами недостающих тулов** (agents.md:597). Шов маппит
   это как `hostError` → задача `failed` с фактической причиной — ограничение
   сообщено системой явно, непроверенные выводы не выдаются (FR-003).
2. **Провайдеры — доказано по коду (веб-разведка, зафиксировано здесь).** В
   этой установке два независимых провайдера: локальное ambient-расширение
   `~/.pi/agent/extensions/web-search/` регистрирует `web_search` и
   `web_fetch` через `pi.registerTool` (extensions/web-search/index.ts:78,
   :199; реализация — curl к SearXNG JSON API и fetch-серверу); глобальный
   пакет `pi-codex-search` регистрирует `codex_search` в `session_start`-хуке
   (pi-codex-search/index.ts:694); при отсутствии конфиг-файлов включён по
   умолчанию (src/config.ts:43 `DEFAULT_ENABLED`), `codex_standalone_web`
   выключен (:48). Оба провайдера — ambient: в background-детей попадают
   автоматически, в foreground — нет (agents.md:551-553). Делегатские дети
   fusion — foreground, поэтому доставка — только явная:
   `subagentOnlyExtensions` (доказанная форма значения — путь к файлу
   расширения: относительный `./…` — правило базового пути для этой формы
   документацией явно не описано, agents.md:409/:569, или абсолютный :588;
   для обязательных расширений путь должен существовать, agents.md:481) или
   path-like запись в `tools` (agents.md:570); npm-имя пакета как значение
   документацией не подтверждено. Для web-пары резолвимый путь есть:
   `~/.pi/agent/extensions/web-search/index.ts`. Для `codex_search`
   резолвимая доставка foreground-ребёнку НЕ доказана: регистрация живёт в
   `session_start`-хуке (срабатывание этого хука в дочернем сеансе не
   проверено), а приёмлемость пути к entry-файлу npm-пакета как значения
   `subagentOnlyExtensions` не подтверждена — явная техническая
   неопределённость (§13, §14 OQ-3), значение не выдумывается.
3. **Политика составов — переносимая и механическая (направление оператора:
   используются оба провайдера, не один) (F1, раунд 3).** Строгий preflight сверяет каждое
   имя `tools` и валит запуск при отсутствии ЛЮБОГО имени (пп. 1), отсюда
   явный запрет: **один профиль со списком «три опциональных имени» не
   обещает запуска** — одно отсутствующее имя валит запуск целиком. Поэтому
   состав веб-инструментов фиксируется явно:
   - конфиг fusion получает поле `researcherWeb` ∈ `none | web | codex |
     both` (дефолт `none` до закрытия OQ-3; после смоука оператор ставит
     нужный состав, целевой по направлению оператора — `both`);
   - составу соответствует ровно один профиль researcher с точным списком
     веб-имён, равным составу: `none` → `fusion-researcher` (без веб-имён),
     `web` → `fusion-researcher-web` (`web_search`, `web_fetch`), `codex` →
     `fusion-researcher-codex` (`codex_search`), `both` →
     `fusion-researcher-both` (все три имени); шов выбирает имя агента по
     конфигу, установщик (§4.6) ставит все варианты и показывает статус
     каждого;
   - доступность fusion НЕ детектирует (TD-09): расхождение конфига с
     окружением ловит preflight — задача `failed` с именем отсутствующего
     тула (§4.10), чинится оператором изменением `researcherWeb`;
     автодеградация состава в рантайме не строится — она требовала бы
     чтения реестра тулов хоста (отвергнуто TD-09) и молчала бы о смене
     окружения;
   - все провайдеры отсутствуют (`none`) — единственный состав, где запуск
     не может провалиться из-за веба: researcher выполняет доступную
     (кодовую) часть и возвращает отчёт с `unknowns` (пп. 5) или
     `needs_orchestrator`, если задача без веба не имеет смысла;
   - runtime-ошибка при наличии тулов (сеть недоступна, SearXNG
     деградировал, авторизация Codex не прошла) — не случай preflight:
     тула зарегистрированы, запуск состоялся; поведение инструкционное
     (пп. 5), механического `failed` нет.
   Поиск + проверка источников по составу: `web` — поиск `web_search`,
   проверка открытием источника `web_fetch`; `codex` — поиск
   `codex_search`, `web_fetch` недоступен ⇒ независимое открытие источника
   невозможно: в `sources` — только URL из выдачи, а `unknowns` прямо
   отмечает, что содержимое источников независимо не открывалось; `both` —
   поиск обоими каналами с перекрёстной сверкой, проверка — `web_fetch`
   (`codex_search` не заменяет fetch); `none` — веб-утверждений нет,
   `sources` только из кода/файлов.
4. **Доставка web-варианта — установщик.** Профили `-web`/`-both` ссылаются
   на web-search-расширение через `subagentOnlyExtensions`; в репозиторном
   файле стоит плейсхолдер `{{FUSION_WEB_EXTENSION_ENTRY}}`, установщик при
   копировании подставляет резолвленный абсолютный путь entry-файла
   (`~/.pi/agent/extensions/web-search/index.ts`; форма `~` для этого поля
   не доказана, поэтому путь резолвится при установке; строка `version:`
   остаётся литеральной — проверка устаревания её не трогает). Отсутствующий
   entry-файл: установка нотифицирует, запуск по agents.md:481 валится
   честно. Профили `-codex`/`-both` содержат `codex_search` в `tools` без
   доказанного механизма доставки: если в живом ребёнке тула не окажется,
   preflight валит запуск с этим именем (пп. 1) — честный отказ вместо
   выдуманной работоспособности; составы `codex`/`both` считаются
   подтверждёнными только после живого смоука (§11).
5. **Инструкционный (агент).** Профиль researcher обязан: помечать
   непроверенное в `unknowns`, не называть веб-исследованием выводы без
   источников. Правило действует при наличии тулов: сетевые/провайдерные
   ошибки во время работы — отчёт с `unknowns`, объясняющим ограничение
   (или `needs_orchestrator`, если задача без веба не имеет смысла).
   Отсутствие самих тулов — не этот случай: до первого хода запуск валится
   (пп. 1, §4.10), механически `failed`.

Проверка доступности веб-провайдера до вызова не добавляется: preflight шва
остаётся проверкой event bus (seam/availability.ts:11-14), дублировать реестр
тулов хоста pi-fusion не будет — хост сам сообщает имена недостающего точнее (TD-09).

## 5. Доступ лида: `write`/`edit` внутри realpath-цели `openspec/` (FR-004)

### 5.1 Точка интеграции

Гейт `registerLeadRestrictions` (restrictions.ts:145-151) сегодня блокирует
тул целиком: `{ block: true, reason }`. Исключение — чистая функция из нового
`lead-access.ts`, вызываемая до блока:

```
block(write/edit) = fusionOn ∧ leadSession ∧ toolBlocked(config.leadBlockedTools)
                    ∧ ¬pathInsideOpenSpecTarget(event.input.path)
```

`event.input.path` — аргумент тула (WriteToolCallEvent/EditToolCallEvent,
pi-coding-agent dist/core/extensions/types.d.ts:945-957); при отсутствии/непохожести
на строку — отказ (консервативно). Фаза лида, баррен-счётчик и тексты отказов
не меняются; отказ вне realpath-границы `openspec/` получает **добавочную строку
причины**: «вне каталога документации OpenSpec код пишут воркеры; исключение
лида ограничено целевым каталогом `openspec/`».

### 5.2 Алгоритм проверки содержимости (lead-access.ts)

1. `projectRoot = ctx.cwd` главной сессии; граница лексически = `join(root, "openspec")`.
2. **Нормализация как у хоста (B2).** Хост открывает не сырую строку, а
   результат `resolveToCwd` (write.js:31, edit.js:94 = `normalizePath` +
   resolve, options `{normalizeUnicodeSpaces, stripAtPrefix}`, `expandTilde`
   по умолчанию). Конвейер хоста (`dist/utils/paths.js`) в фиксированном
   порядке: Unicode-пробелы → пробелы (`UNICODE_SPACES` :6, замена :61-63),
   снятие ведущего `@` (:64-66), на win32 перевод `/c/…`-форм (git-bash/
   cygwin/wsl) в `C:\…` — и только если путь начинается с `/`, не `//` и
   не содержит `\` (`normalizeWindowsShellPath` :50-58, условие :51),
   раскрытие `~`/`~\` в домашний каталог (:70-78), последним `file://` →
   файловый путь через `fileURLToPath` (:79-81); затем resolve (:83-87).
   Гейт проверяет ровно этот результат: lead-access реплицирует набор
   преобразований и их порядок — контракт паритета (хостовая утилита из
   корня пакета не экспортируется — проверено по `exports`), каждый шаг
   закреплён parity-тестом (§11); затем `path.resolve(root,
   <нормализованное>)` — `..` нейтрализуется самим `resolve` (лексически).
   Непарсируемое значение (например, битый `file://`) — отказ,
   консервативно.
3. **Реальный путь; существование — по `lstat` (F2).** Существование каждого
   компонента пути определяется `lstatSync`: ссылка существует, даже если её цель
   висит. Для каждого компонента, существующего по `lstat`, вызывается
   `fs.realpathSync`; если вызов бросает исключение (включая dangling symlink/
   junction), доступ отклоняется. Это правило действует для кандидата, всех его
   предков и самой границы `openspec` (включая dangling-ссылку в любом предке
   границы). Подъём nearest-existing-ancestor для новых файлов пропускает только
   отсутствующие обычные компоненты; каждый существующий компонент проверяется,
   и ни один `realpath`-сбой не трактуется как «путь отсутствует». Хостовая
   `canonicalizePath` (`dist/utils/paths.js:13-20`) при ошибке молча возвращает
   сырой путь и запрещена: silent-fallback вернул бы непроверенный путь.
   **Граница `openspec` следует ссылке (OQ-4, решение владельца 2026-11-01):**
   `boundaryLexical = join(realpath(root), "openspec")`; если путь существует,
   `boundaryReal = realpath(boundaryLexical)`. Цель симлинка/junction и становится
   границей, даже если находится вне корня проекта. Кандидат разрешён, если его
   канонический путь лежит внутри `boundaryReal`; кандидат за этой границей
   отклоняется. Если `openspec` ещё не существует, граница для первого запуска —
   `realpath(root)` с лексическим хвостом `openspec/...`; создание каталога write-тулом
   остаётся разрешённым. На Windows необходимость `fs.realpathSync.native` для
   junction-кейсов не подтверждена — реализация проверяет это ручным
   junction-тестом (§11, §13).
4. **Сравнение.** `rel = path.relative(boundaryReal, candidateReal)`; разрешено,
   если `rel !== ""`, первый компонент `rel` не равен `..` (проверяется
   **компонент**, не префикс строки: допустимое имя `..notes` не должно
   отвергаться) и `rel` не абсолютен. На win32 `path.relative` сравнивает
   префикс без учёта регистра и нормализует `/` vs `\`.
   **База сравнения при первозапуске:** если `openspec` ещё не существует,
   сравнение выполняется против лексической базы `join(realpath(root),
   "openspec")` (без realpath — его взять неоткуда), а `candidateReal` несёт
   лексический хвост после ближайшего существующего предка. Сравнение с голым
   `realpath(root)` запрещено: это fail-open — любая запись в корне проекта
   проходила бы вне границы (нарушение FR-004).

### 5.3 Windows

- Сравнение через `path.*` платформенно-корректно: регистр (`C:\AI` ≡ `c:\ai`),
  разделители, disk-letter префикс.
- UNC-пути (`\\server\share\...`) и device-формы (`\\?\C:\...`) сравниваются
  тем же механизмом. Для пути другого тома `path.relative` на Windows может
  вернуть **абсолютный** путь, а не `..`-хвост, — поэтому явная проверка
  абсолютности `rel` (§5.2.4) обязательна и именно она даёт отказ.
- Подстановок env в пути тула нет, но хост **не** передаёт строку как есть:
  `~` раскрывается, `@` снимается, Unicode-пробелы нормализуются, `file://`
  распознаётся (§5.2.2). Гейт проверяет тот же результат, который откроет
  хост; проверка сырой строки означала бы проверку не того пути.

### 5.4 Ссылки (symlink/junction)

- Если сам `openspec/` — существующая ссылка, её `realpath`-цель становится
  границей; разрешена запись внутри цели, даже если она вне корня проекта
  (OQ-4, утверждено владельцем). Это не отменяет проверки вложенных компонентов.
- Ссылка внутри реальной границы `openspec/`, указывающая за её пределы:
  `realpath` кандидата вне `boundaryReal` → отказ.
- Существующая ссылка вне границы, указывающая внутрь неё: цель внутри →
  разрешено (запись фактически попадает в защищённый каталог).
- Висячая ссылка в любом компоненте пути кандидата, границы `openspec/` или
  предках этих путей: обнаруживается `lstat` до `realpath` (§5.2.3) → отказ,
  fail-closed; в ветку «несуществующий файл» не попадает.
- Жёсткие ссылки (hardlink) realpath'ом не обнаруживаются: файл внутри границы,
  являющийся hardlink'ом узла снаружи, пройдёт проверку и запишет общий инод —
  остаточный риск (§5.5), не гарантия.

### 5.5 Проверяемая граница (формулировка FR-004)

Проверенное поведение: лексические `..`, абсолютные пути вне границы
`boundaryReal`, вложенные symlink/junction-эскейпы за пределы границы,
следование ссылке в самом `openspec/` по OQ-4 (цель может быть вне корня
проекта), dangling-ссылки в любом компоненте и предке (F2, §5.2.3),
отсутствующие файлы (nearest-existing-ancestor), регистронезависимость и
разделители Windows, другой том, нормализация входа до хостовой (`~`, `@`,
Unicode-пробелы, `/c/…`-формы, `file://` — §5.2.2) и выход за границу после
нормализации.

Не проверяется и не гарантируется (остаточные риски): TOCTOU-гонка
(цель `openspec/` или вложенная ссылка/каталог может быть подменена между
проверкой и записью — проверка и запись не атомарны), hardlink-алиасы (§5.4),
эффекты со стороны самих тулов host'а вне нашего контроля. Следование ссылке
за пределы проекта — сознательное решение владельца, не гарантия изоляции.
Никакой изоляции не заявляется (requirements, «Вне объёма»): за пределами
перечисленного безопасность исключения держится на инструкции лида и доверии
оператора.

## 6. Доверительный Perl через bash (FR-005)

### 6.1 Точка интеграции и форма разрешения

Тот же гейт (restrictions.ts:145-151), тул `bash`, `event.input.command`:

```
block(bash) = fusionOn ∧ leadSession ∧ toolBlocked ∧ ¬isSinglePerlInvocation(command)
```

`isSinglePerlInvocation` — чистый токенайзер в `lead-access.ts`. Разрешается
**ровно один вызов** `perl` с аргументами, без участия оболочки как
интерпретатора цепочки:

1. trim; первый токен строго `perl` (не `perl5`, не `/usr/bin/perl`, не после
   `env`/`cd`/`sudo`).
2. Сканер POSIX-подобного квотинга: пробелы вне кавычек разделяют токены;
   `'…'` — литерал без исключений; в `"…"` запрещены `$`, backtick и обратный слеш "\"
   (консервативно). Запрет backslash в двойных кавычках обязателен:
   bash раскрывает `\`-эскейпы внутри двойных кавычек, и `\"` **не закрывает**
   строку для оболочки, хотя «переключатель кавычек» без учёта escape
   закрывает её — сканер расходится с bash и прячет хвост команды. Воспроизведённый
   обход: `perl -e "x\" " ; echo SHELL_CHAIN_EXECUTED; #"` — для сканера без
   обработки escape весь хвост «внутри строки», bash же исполняет `echo`
   второй командой. Запрет закрывает обход; воспроизведение — обязательный
   отказ-тест (§11). Руководство лиду — передавать программу в одинарных
   кавычках.
3. Вне кавычек запрещены: `; | & ( ) < > ` $` и переводы строк/CR, а также `\`
   (экранирование не поддерживаем — проще отказать, чем эмулировать shell).
4. Незакрытая кавычка → отказ. Результат — argv; `argv[0] === "perl"`.
5. **Применимость классификатора (shellPath, fail-closed).** Классификация
   честна только для POSIX-совместимой оболочки. Хост допускает пользовательский
   `shellPath` (settings.json → settings-manager.js:760-762, попадает в bash-тул
   через `getShellConfig`, bash.js:133). Процедуры подтверждения
   POSIX-совместимости не существует, поэтому правило механическое: **любой
   заданный `shellPath` отключает perl-исключение** — полный блок bash
   (fail-closed). Гейт узнаёт настройку через хост-конфиг; если настройку
   прочитать не удалось — тоже отказ исключения.
6. Классификатор **не** проверяет, что perl работает с `openspec/`: произвольный код
   непрозрачен; рамка «документация проекта» — инструкция (§6.2, §7), не проверка.

Оговорка к «ровно один вызов» (shellCommandPrefix): классификатор проверяет
строку `command` тула; хост перед исполнением добавляет настроенный оператором
префикс (`${commandPrefix}\n${command}`, bash.js:160, :173). Префикс —
доверенная настройка оператора, классификации не подлежит; «ровно один вызов»
утверждается про переданную команду, общая рамка доверия — §6.2.

Примеры: разрешено `perl -0777 -i -pe 's/foo/bar/g' openspec/config.yaml`,
`perl -e 'print 42'`; отклонено `echo x | perl -e …`, `perl -e 'x' && rm -rf /`,
`perl -e "print $ENV{HOME}"` (двойные кавычки с `$`), `perl -e 'a'; perl -e 'b'`,
`` perl `ls` `` (первый токен не perl), `perl -e 'x'
rm -rf /` (перевод строки), `perl -e "x\" " ; echo …` (backslash в двойных
кавычках — обход B1, §6.1.2).

### 6.2 Ограничения безопасности — явные негарантии (обязательная рамка)

- **Это не песочница.** Произвольный Perl может читать/писать любые файлы,
  запускать процессы (`system`, `exec`, `open "|…"`, backticks внутри кода) —
  в т.ч. **вне `openspec/` и мимо свойства «один вызов»** на уровне ОС. Классификатор
  отвечает только за «команда — ровно один вызов perl», и не более того
  (FR-005: «цепочка shell не считается разрешённой из-за слова perl» —
  выполняется именно этим: `foo | perl`, `perl && …`, подстановки `$()` —
  отказ).
- Ограничение использования документацией — инструкция секции `### fusion`
  (§7) + доверие оператора (решение D-002). Изоляция файловой системы **не**
  обеспечивается и не заявляется (requirements, «Вне объёма»).
- Слово «perl» в произвольной позиции (`echo perl`, `xperl`, `perlfoo`) не
  разрешает команду — проверяется первый токен и целостность токенайзера.

### 6.3 Windows

`bash`-тул хоста на Windows исполняет команды через bash-совместимую среду
(git-bash/WSL): квотинг оценивается по POSIX-правилам, как в §6.1. Если
оператор переопределил `shellPath` (settings-manager.js:760-762 → bash.js:133),
совместимость квотинга не гарантируется и perl-исключение отключается целиком
(§6.1.5: любой заданный `shellPath` = исключение выключено, fail-closed). Доступность
`perl` — свойство среды (в типичном git-bash есть); отсутствие перла — обычная
ошибка тула («command not found»), возвращаемая лиду как результат bash: гейт
пропустил, среда честно отказала. Фолбэков на другие шеллы нет.

## 9. Security / Permissions / Privacy (негарантии — обязательный раздел)

1. Ролевые `tools`/`toolBudget.block` — сужение поверхности, не изоляция:
   reviewer/researcher/scout без `edit`/`write` всё ещё могут писать через
   разрешённый `bash` (reviewer) или быть переопределены руководством
   оператора: приоритет builtin < package < user < project (agents.md:17-24),
   проектный уровень `.pi/agents/` при доверии к проекту перекрывает `fusion-*`
   (agents.md:34, «Where agents live»).
2. Исключение `openspec/` — проверяемая realpath-граница с остаточными рисками
   (§5.5): TOCTOU, hardlink, неатомарность. Цель самой ссылки `openspec/`
   может лежать вне корня проекта по явному решению OQ-4; это доверенный каталог,
   не песочница. Дефолтный блок `leadBlockedTools` включает `powershell` по OQ-1;
   блокировка безвредна на хостах, где такого тула нет. Перл-исключение к
   powershell не применяется.
3. Perl-исключение — доверие, не песочница (§6.2): произвольный Perl может всё.
4. Секция `### fusion` — инструкция модели; модель может нарушить инструкцию;
   механический слой (гейт) остаётся единственным принуждением, и его границы —
   пп. 2-3.
5. Ничего из этого не противоречит FR-003/FR-005: требования прямо запрещают
   заявлять изоляцию — дизайн соблюдает запрет и фиксирует границы проверяемого.

## 10. Edge Cases (сводно)

- Смешанный fan-out (разные роли в одном вызове): поддержан — роль на задачу,
  общая очередь/ротация; клампы считаются по задачам, не по ролям.
- `needs_orchestrator` от любой роли: конверт с if/then требует `question`;
  текст отказа лида ведёт новый fan-out с ответом (restrictions.ts:98-102) — без изменений.
- Reviewer вернул `verdict: "fail"`: это `status: "done"` ревью-задачи
  (ревью выполнено); решение о переделке — лид, через новый fan-out.
- Scout/researcher с непустым `filesChanged` (нарушил инструкцию): механически
  не отклоняется; поля честно отображаются лиду; `no_changes ⇒ filesChanged=[]`
  валидируется как сегодня (report/validate.ts:44-52).
- `openspec/` — симлинк/junction на каталог вне проекта: по утверждённому OQ-4
  границей становится `realpath` цели; запись внутри реальной цели разрешена,
  выход за её пределы отклоняется. Dangling-ссылка любого компонента пути по-прежнему
  fail-closed (OQ-4 не разрешает висячие цели). TOCTOU и hardlink-алиасы остаются
  рисками (§5.5): проверка не атомарна.

## 11. Testing / Verification Strategy

- **Unit (чистые функции):** таблица кейсов perl-классификатора (§6.4) —
  разрешающие и отказывающие формы, включая обязательный отказ-тест на
  воспроизведение обхода B1 `perl -e "x\" " ; echo …` (backslash в двойных
  кавычках, §6.1.2) и отказ при не-POSIX-совместимом `shellPath` (§6.1.5);
  таблица path-резолвера: POSIX и win32
  (`path.win32`-ветки тестируются на любой ОС через инъекцию платформенного
  модуля), `..`, абсолютные вне границы, symlink (создаётся в temp-каталоге
  теста), отсутствующий файл, отсутствующая `openspec/`, `openspec` — ссылка
  за пределы корня проекта → запись внутри realpath-цели разрешена (OQ-4); ссылка
  внутри цели на путь за её пределами → отказ; dangling-ссылка в кандидате,
  любом предке или самой границе `openspec/` → отказ через `lstat` + `realpath`
  (F2, §5.2.3); регистр/разделители,
  компонентная проверка `..` (имя `..notes` — допустимо, §5.2.4).
  **Parity-тесты нормализации с хостом (B2):** имя с NBSP, ведущий `@`,
  `~/…`, win32 `/c/…`-форма, `file://` — гейт проверяет тот же путь, который
  откроет хост (`resolveToCwd`-семантика, §5.2.2); эскейп наружу после
  нормализации.
- **Component (fake-pi):** гейт с `input: { path }` / `{ command }`
  (формат события — test/restrictions.test.ts:33): пропуск/блок по realpath-границе,
  включая top-level openspec symlink наружу, вложенную ссылку за пределы цели,
  dangling-кандидат и dangling-предка; perl-форма; `powershell` blocked by default
  (безвредно при отсутствии тула); тексты причин; guidance-строки.
- **Интеграция (fake-pi + шов):** ролевые `:request` (§4.11); ролевые отчёты →
  `TaskResult`; ретрай ролевой схемы; полный ретрай-путь до `renderFanoutText`
  с ролевыми полями (B3, §4.8); состав корректива: бриф, size-limited прошлый
  ответ при наличии — с тестом, что значение доходит от `SeamOutcome` до
  `runReportRetry`, честная недоступность при host-refused, report-only
  формулировка (B4, §4.5); установка
  манифеста и командный путь `turnFusion` с устаревшим профилем → `updated`
  (B6, §4.6); командный путь не обновляет существующие `current`-профили.
- **Пины неизменности:** worker-ветка шва/схемы/блока — побайтово; клампы/окно —
  существующие тесты без правок.
- **Ручной смоук (после реализации, вне этой задачи; веб-матрица обязательна
  для OQ-3, ещё НЕ проводилась).** Каждый веб-состав — в своём отдельном
  окружении: (a) `web`: web-search-расширение есть, pi-codex-search
  отсутствует → `fusion-researcher-web` запускается, `web_search`+`web_fetch`
  зарегистрированы до первого хода, поиск и открытие источника работают;
  (b) `codex`: pi-codex-search есть → `codex_search` регистрируется в живом
  ребёнке, авторизация Codex подтверждается реальным вызовом; (c) `both`:
  оба провайдера → все три имени зарегистрированы, перекрёстный поиск +
  `web_fetch`; (d) `none`: профиль без веб-имён запускается, отчёт с
  `unknowns`; (e) негативный пин честности: профиль состава `both` в
  окружении без одного из провайдеров → preflight валит запуск с именем
  отсутствующего тула (§4.9.1, §4.9.3). Остальной смоук: живой вызов с
  ролью **researcher** при несоответствии состава окружению → задача
  `failed` с именами тулов; отдельно **scout**
  (без веб-тулов в профиле) успешно работает без провайдера; кейс
  нормализации (имя с NBSP или `~/`) — гейт и хост открывают один путь;
  `write` в `openspec/` и `perl -e '…'` лидом при fusion on; `write` вне `openspec/` —
  отказ.

## 12. Technical Decisions

- **TD-01: роль — нормализованное поле задачи.** Альтернатива — отдельный
  параметр тула верхнего уровня: отвергнуто, роль принадлежит задаче (разные
  роли в одном fan-out), а нормализация в валидаторе убирает опциональность из
  даунстрима (прецедент — `title`, contract/validate.ts:199-203).
- **TD-02: роли = файлы-профили pi-subagents + установщик.** Альтернатива —
  runtime-регистрация агентов через API pi-subagents: меньше файлов, но теряется
  наблюдаемость установки (FR-006), редактируемость оператором и единый путь с
  существующим `fusion-worker` (worker-install.ts). Тихий фолбэк на worker при
  отсутствующем профиле отвергнут: честная ошибка лучше молчаливой подмены роли.
- **TD-03: без модели по роли (D-001).** Ротация `workerModels` общая; в
  профилях нет `model:`/`thinking:`; per-run модель шва сильнее frontmatter
  (docs/models.md, порядок приоритета). Ревьюер на другой модели — забота
  оператора расширением ротации, не кода.
- **TD-04: общий конверт отчёта + ролевые надстройки; TaskResult — additive.**
  Альтернатива — отдельные output-схемы на роль без общего конверта: дублирует
  if/then-правило и ломает переиспользование ретрая/маппинга (fanout.ts:189).
- **TD-05: двойное сужение (allowlist профиля + block шва).** Allowlist —
  первичное средство pi-subagents; block шва страхует рассинхрон версий
  профилей. Оба слоя документированы как сужение, не изоляция (§9.1).
- **TD-06: realpath + nearest-existing-ancestor + path.relative.** Альтернативы:
  лексическая проверка (пропускает symlink) — отвергнута; полный анти-TOCTOU
  (openat-подобная атомарность) — вне досягаемости tool_call-хука хоста, честно
  зафиксировано как остаточный риск (§5.5). Нормализация входа реплицирует
  хостовую `resolveToCwd` (преобразования write/edit — §5.2.2): проверка сырой
  строки означала бы проверку не того пути, который откроет хост (B2).
- **TD-07: строгий токенайзер одиночного вызова perl.** Альтернативы: блок
  bash целиком (текущее F19) — не выполняет FR-005; разрешать по префиксу
  «perl» без токенайзера — прямо запрещено FR-005 (слово perl ≠ разрешение).
  Экранирование `\` вне кавычек отвергнуто (упрощение в сторону отказа);
  backslash в двойных кавычках тоже запрещён — bash раскрывает `\"`-эскейпы
  и «переключатель кавычек» расходится с оболочкой (B1, §6.1.2).
- **TD-08 (утверждено владельцем 2026-11-01, OQ-1): `powershell` в дефолтном
  гейт-списке.** Хост объявляет тул `powershell` (pi-coding-agent
  dist/core/tools/index.d.ts:23, ToolName); поэтому он добавляется к дефолтному
  `leadBlockedTools` (`write`, `edit`, `bash`, `powershell`) и закрывает обход F19
  на Windows. Если конкретный хост не предоставляет этот тул, его наличие в
  списке безвредно. Пользовательские явно заданные списки не переписываются
  автоматически. Исключение perl на powershell **не** переносится.
- **TD-09: честность веба — состав из конфига + preflight ребёнка +
  инструкция, без своего детектора провайдера.** Доказано: foreground-ребёнок
  не грузит ambient-расширения (agents.md:551-553), явные тула сверяются с
  реестром до первого хода, недостающие валят запуск с именами
  (agents.md:597); `subagentOnlyExtensions` принимает пути к файлам
  расширения (agents.md:409, :569, :588), npm-имя пакета документацией не
  подтверждено. Провайдера два, оба установлены (доказано по коду, §4.9.2):
  web-search-расширение (`web_search`/`web_fetch`) и `pi-codex-search`
  (`codex_search`). Направление оператора — использовать оба; состав
  фиксируется конфигом `researcherWeb`, и по составу выбирается ровно один
  профиль; список «опциональных имён» в одном профиле запрещён (§4.9.3).
  Дрейф окружения fusion не детектирует — его ловит preflight (`failed` с
  именами). Недоказанное (не выдумывать): доставка `codex_search`
  foreground-ребёнку (`session_start`-хук в дочернем сеансе, путь к
  entry-файлу npm-пакета в `subagentOnlyExtensions`), форма `~` в значении,
  живое поведение preflight, Codex-авторизация и здоровье SearXNG в
  рантайме — предмет OQ-3; без живого смоука (§11) FR-003 не реализуется
  (§4.9, §13).
- **TD-10: бриф не знает о роли.** `renderBrief` (briefs.ts:66) не
  меняется; ролевая рамка живёт в системном промпте профиля. Меньше поверхность
  изменений, контракт-блок остаётся общим контекстом для всех ролей.

## 13. Known Risks

- Точный код ошибки шва при несуществующем агенте (`invalid_request` vs
  `failed`) определяется адаптерами pi-subagents; тест на fake-pi закрепляет
  маппинг, живой смоук подтверждает (§4.10).
- **БЛОКЕР (OQ-3, этим дизайном не закрыт):** живое подтверждение доставки
  веб-тулов foreground-ребёнку. Политика составов задана (§4.9.3): конфиг
  `researcherWeb`, по составу — ровно один профиль, «опциональные имена»
  одним списком запрещены. Доказано по коду: оба провайдера ambient
  (`web_search`/`web_fetch` — registerTool,
  extensions/web-search/index.ts:78/:199; `codex_search` —
  session_start-хук, pi-codex-search/index.ts:694, default enabled);
  npm-имя пакета как значение `subagentOnlyExtensions` документацией не
  подтверждено (agents.md:409/:569/:588 — только пути к файлам). Не
  доказано и не выдумывается: срабатывание `session_start`-хука в дочернем
  сеансе, приёмлемость пути к entry-файлу npm-пакета, форма `~` в значении,
  Codex-авторизация и здоровье движков SearXNG в рантайме, фактическое
  поведение preflight в живом прогоне. Живой смоук матрицей (web / codex /
  both / none в отдельных окружениях + негативный пин, §11) НЕ проводился;
  до него FR-003 не считается обеспеченным. Состав `none` и механический
  отказ при несоответствии состава окружению (§4.9.1, §4.9.3) доказаны и
  остаются честным поведением при любом раскладе.
- Windows-ветки path-резолвера тестируются на CI не-Windows только через
  `path.win32`-инъекцию; реальные junction-кейсы покрывает ручной смоук.
  Не подтверждена также необходимость `fs.realpathSync.native` для
  junction-кейсов (§5.2.3) — реализация закрывает вопрос ручным
  junction-тестом до закрытия задач §5.
- Токенайзер perl консервативен: отдельные легитимные формы (например, абсолютный
  путь к perl-бинарнику) отклоняются; backslash в двойных кавычках отвергнут
  из-за расхождения с bash-эскейпами (§6.1.2); при не-POSIX-совместимом
  `shellPath` исключение отключается целиком (§6.1.5). Руководство лиду —
  каноническая форма `perl …` первым токеном в одинарных кавычках (§6.1).

## 14. Open Questions (к design-ревью оператора)

1. **OQ-1 — answered (утверждено владельцем 2026-11-01):** добавить
   `powershell` в дефолтный `leadBlockedTools` вместе с `write`, `edit`, `bash`.
   Тул блокируется, если хост его предоставляет; если тула нет, запись в список
   безвредна. Исключение Perl на `powershell` не распространяется. Реализация
   config.ts и тест дефолта обязательны.
2. Состав инструкций ролевых профилей (точные тексты системных промптов) —
   предлагается в tasks-фазе как приложение к design, правки требований не требуют.
3. **OQ-3 (БЛОКЕР, обязателен до реализации FR-003): веб-доступ researcher.**
   Направление оператора зафиксировано: используются **оба** провайдера —
   `web_search`/`web_fetch` и `codex_search`. Переносимая политика составов
   задана (§4.9.3): конфиг `researcherWeb` ∈ `none|web|codex|both` (дефолт
   `none`), по составу — ровно один профиль, «опциональные имена» одним
   списком запрещены. Остаётся недоказанным (техническая неопределённость,
   §13): доставка `codex_search` foreground-ребёнку (`session_start`-хук в
   дочернем сеансе; путь к entry-файлу npm-пакета как значение
   `subagentOnlyExtensions`), форма `~` в значении, живое поведение
   preflight, Codex-авторизация и здоровье SearXNG в рантайме. Обязателен
   живой смоук в отдельных окружениях: web-вариант, codex-вариант, both,
   none + негативный пин «профиль `both` в окружении без одного провайдера →
   preflight `failed` с именем» (§11); **смок ещё не проводился**. Без него
   FR-003 не реализуется: недоказанное не выдумывается (§4.9, §13).
4. **OQ-4 — answered (утверждено владельцем 2026-11-01): следовать ссылке.**
   Если `openspec/` проекта — действующий symlink/junction, границей исключения
   становится `realpath` его цели, даже когда цель вне корня проекта; доступ
   разрешён только внутри этой realpath-цели. Любой dangling-компонент пути
   остаётся отказом (OQ-4 не разрешает висячие ссылки). Вложенные ссылки,
   выходящие за границу цели, отклоняются. TOCTOU и hardlink остаются
   остаточными рисками (§5.5, §10).
